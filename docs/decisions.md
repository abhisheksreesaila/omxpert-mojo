# Decisions

- D-01 · own git repo inside expert-dispatch over a new top-level repo · the parent is not git and holds the model tools and data · yes
- D-02 · Mojo 1.2.0 + MAX 26.7.0 release over the Oct nightly in ../max · matches the Modular source checked out today · yes
- D-03 · reuse llama.cpp for attention/linear attention/n-gram, own only the expert layer · a full qwen4exp forward pass in Mojo is weeks; the measured gap is in the MoE dispatch · yes
- D-04 · write our own Q4_K/Q5_1 GPU GEMV · MAX has Q4_K only on CPU and Q4_0/GPTQ on GPU · yes
- D-05 · fp32 activations with per-element dequant over int8 activations + integer dots · keeps error ~3e-7 vs float64 (milestone bar 1e-3) and matches the reference; int8 would make order irrelevant (exact) but changes numerics; revisit if CPU or GPU becomes ALU-bound · yes
- D-06 · fold Q5_1's offset as d*sum(q h) + m*sum(h) on both devices · one fma per value instead of two; it's a definition of the order, applied identically on CPU and GPU · yes
- D-07 · gate/up: one row pair per warp with x in registers, over multi-row and split-warp variants · measured best (32.8 vs 38-47 us) · yes
- D-08 · M2 CPU speed judged on the median of 5 runs, not one · desktop load (Chromium) moves single runs by +-1.5 GB/s; the skill's noise rule; threshold unchanged · yes
- D-09 · keep two parallelize calls per layer for now; persistent pthread workers come with the mailbox in M3 · fused spin-barrier version was 2.8x slower with the runtime's task model · yes
- D-10 · pins: same budget (35000 MiB) and same rule as the EDX patch (split by free VRAM, profile score order), not llama.cpp's exact per-group slot counts (not logged at this verbosity) · hit share 92.8% vs night 6's ~94% shows placement is not what makes the difference · yes
- D-11 · llama.cpp's MoE cost measured by subtraction (EDX_NOMOE drops routed experts + router from the graph) · no profiler on the box; includes the scheduler/split overhead MoE causes, which is part of MoE's real cost · yes
- D-12 · CPU co-processor = persistent pthreads from Mojo (abi("C") entry) polling the mailbox, over parallelize() · 1 us vs 236 us per dispatch; parallelize was 60-70% of every cold request · yes
- D-13 · page out hot experts' file pages after their VRAM copy · without it cold experts were read from SSD (650 MB/s of faults); same as llama.cpp's EDX_PAGEOUT, so the comparison stays fair · yes
- D-14 · integrate as a shared library called from a ggml custom op (host round trip per layer) before any in-stream / megakernel integration · smallest change that measures the real end-to-end effect; the round trip turned out cheap (~150 us/layer call total) · yes
- D-15 · prompts through the Mojo layer token by token (OMX_PREFILL) · llama.cpp's own prompt path reads every expert from mmap and evicts the cold set (8 tok/s); token-by-token gives 112 tok/s; batched kernels are the next step · yes
- D-16 · -lzm on (n-gram/Engram rows on demand) for the Mojo runs, and the same flags for the control · frees ~29 GB of RAM for cold experts; the control shows the flags alone don't speed llama.cpp up · yes
- D-17 · M5 proof checks recorded runs by default (FULL=1 reruns ~30 min of server runs) · keeps scripts/check usable; the scripts that produced the numbers are in ../scripts · yes
- D-18 · M6 left FAILING with the evidence instead of redefining it · GOAL rules; the measured cold-union growth (3.62x at 5 tokens) makes its bar impossible on this data. Proposed replacement milestones (batched layer for prompts; MTP-drafted speculation) need the owner's nod since they change the plan · yes
- D-19 · timing proofs (m1, m2, m4) wait for a quiet machine first (scripts/wait_quiet.sh) · a full check during heavy desktop load (load 26, Chrome ~11 cores) failed M2/M4 on speed while bits stayed identical; thresholds unchanged · yes
