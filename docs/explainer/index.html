omxpert · Qwen3.8-Flash-Next · 2× RTX 3090 · notes from 16–17 Nov 2026

A 125B model on a desktop, 1.5–1.7× faster — frame by frame

What a token goes through inside a mixture-of-experts transformer, why llama.cpp spent most of its time on one part of it, and the ~2,700 lines of Mojo that replaced that part. about 50 tok/s instead of 26–32, with output that stays bit-identical wherever each expert runs.

FRAME 01 · THE PROBLEM

The model is bigger than the graphics cards

Qwen3.8-Flash-Next has 125 billion parameters plus a 51-billion-entry n-gram table. At 4 bits that is a 111 GB file. Your two RTX 3090s hold 48 GB. RAM holds 62 GB, and your desktop uses some of both.

Graphics memory is fast (838 GB/s per card); RAM is about 30× slower (26 GB/s). Everything below is about deciding which bytes live where.

FRAME 02 · A TOKEN'S JOURNEY

Every new word walks through 48 layers

The model writes one token (a word piece) at a time. The token becomes a vector of 2,560 numbers, then passes through 48 layers. Each layer has two parts: attention, which looks back at the conversation, and a mixture of experts, which does most of the thinking. At the end, a final layer scores all 248,320 possible next tokens.

FRAME 03 · MIXTURE OF EXPERTS

512 experts per layer, 10 at work

Each layer holds 512 small networks called experts, about 3 MB each. A tiny router scores them all for the current token and only the top 10 run. That is why a 125B model reads only a few GB per token: most of it sits idle for any given word.

Which 10 win changes from token to token and layer to layer. That unpredictability is what makes running this on a small machine hard.

FRAME 04 · YOUR EXPERTS

Your conversations use a small part of the model

We ran the model over your own chat history and counted which experts fired. About half the experts serve 93% of your picks. Those go on the graphics cards: the hot set. The rest, the cold set, stay in RAM and run on the CPU when needed.

A profile from someone else's work (a coding corpus) covered only 44%. The profile has to be yours.

FRAME 05 · WHERE THE TIME WENT

llama.cpp spent 70% of each token on the experts

We measured llama.cpp's own pinned setup (same profile, 35 GB of hot experts): 35.7 ms per token. Removing the experts from the run left 11.0 ms. So the experts cost 24.7 ms, and the rest of the model only 11.

The graphics cards sat idle 60–80% of the time while one CPU thread ran at 98%, scheduling work. The cost was coordination, not arithmetic.

FRAME 06 · THE SPLIT

Keep llama.cpp, replace its expert engine

llama.cpp keeps attention, the n-gram table, sampling and the server. At each layer's experts, a 60-line hook calls into libomxmoe.so, a library written in Mojo, with the token's vector (10 KB) and gets the result back.

Inside, the router and the top-10 run on the GPU, hot experts run on the GPU, cold experts run on the CPU, and the two meet in a shared mailbox.

FRAME 07 · TRICK 1

One piece of code, two kinds of chip, identical bits

The expert math is written once, with a width setting. On the GPU, width 1: each of a warp's 32 threads owns one lane. On the CPU, width 32: all lanes sit in one SIMD vector. Each lane does the same multiply-adds in the same order, and the lanes are summed by the same tree.

Floating-point results depend on order, so this matters: an expert gives the same bits whether it ran on the GPU or the CPU. 1,200 / 1,200 tokens identical

same Mojo function · W=1 per GPU thread · W=32 per CPU vector
FRAME 08 · TRICK 2

The GPU and CPU pass notes in shared memory

Some RAM is pinned: GPU kernels can read and write it directly. When the top-10 includes cold experts, the GPU writes their ids and the token's vector there, then bumps a sequence number. The CPU sees it, computes, writes results and a done flag. The GPU's combine step waits only for that flag.

No host round trip, no synchronize call. 2 µs per exchange. A ring of 16 slots lets the GPU run ahead on tokens with nothing cold.

seq → work → done · measured round trip 2.06 µs
FRAME 09 · TRICK 3

A CPU that is always awake

Mojo's built-in way to use all cores, parallelize(), cost 236 µs just to start, more than the work itself. So the layer keeps 12 threads alive and spinning, made from Mojo through the operating system's thread API. One watches the mailbox; on a request, all 12 split the expert's rows and meet at an atomic barrier.

Wake-up dropped to 1 µs.

microseconds to wake all cores and wait for them · log-free, to scale
FRAME 10 · TRICK 4

Make room in RAM for the right bytes

Cold experts were being read from the SSD at 650 MB/s. Two things filled RAM instead: the hot experts' file pages, left behind after their copy to the GPU, and the 28.8 GB n-gram table. We release the hot pages after loading, and read n-gram rows only when a token needs them.

The same Mojo MoE went from 36 to 8.6 ms per token.

FRAME 11 · THE RESULT

42 tokens per second, and full context

Same model, same chat prompts, same machine, measured back to back. llama.cpp's pinned stack: 25.9–31.9 tok/s across runs. With the Mojo expert layer: 41.9–44.6, using less VRAM for hot experts.

At full context it holds up: a 26,500-token document is read at 194–214 tok/s (llama.cpp 163–164) and the hidden code in its middle is found.

Greedy text was byte-identical with half the hot experts moved to the CPU. placement-invariant

FRAME 12 · WHAT DIDN'T WORK

Two honest limits

Short prompts trailed: batching took them from 112 to 180–190 tok/s, but llama.cpp does 224. Long prompts beat it, because big chunks upload their busiest cold experts to the GPU while the CPU takes the rest. fixed next day, frame 14

A guess that failed: we expected back-to-back tokens to reuse cold experts, so checking several drafted tokens at once would be cheap. Your trace says no: 5 tokens need 3.6× the cold experts of one. The hot set is personal; the cold picks are a scattered long tail. milestone 6 falsified

FRAME 13 · TRICK 5

Stop stopping the GPU

Until now, at each of the 48 layers llama.cpp paused its GPU and handed the vector to the CPU, which started Mojo's kernels and waited for them. We measured both parts: llama.cpp's pauses cost 1.2 ms per token, Mojo's own wait after each layer about 3 ms.

Now Mojo puts its kernels straight into llama.cpp's own GPU queue: both use the same CUDA context, so Mojo can adopt llama.cpp's stream. The GPU never pauses; cold experts still go to the CPU through the mailbox.

That also lets CUDA graphs work: llama.cpp records a token's GPU launches once and replays them, now with Mojo's kernels inside. A replay can't take fresh numbers from the host, so the GPU numbers its own mailbox notes from a counter in pinned RAM. 72 / 72 replays bit-identical

FRAME 14 · THE RESULT, AGAIN

50 tokens per second, and faster at full context

The new path left about 4 GB idle on each card. It now holds 1,700 more hot experts: 92% of your picks land on the GPUs, up from 88%, so the CPU has a third less to do.

Back to back against the previous night's setup: short chat 49–54 vs 41 tok/s, decode after a 25,000-token prompt 38 vs 30, short prompts 221–258 vs 189 (llama.cpp: 224). The code hidden at 26,500 tokens is still found.

FRAME 15 · NEXT

Where this goes next

The CPU is now the bottleneck. Most of the remaining expert time is the CPU working through cold experts at about 16 GB/s, against 26 GB/s of RAM bandwidth.

Speculation, tested and off: speed-up = accepted tokens ÷ (draft time + check cost). Drafting is nearly free here because the GPUs wait on the CPU, but checking 3 tokens costs 2.4× the expert work, because each new token picks new cold experts. As hot coverage climbs past ~96%, that cost falls toward 1× and speculation starts to pay.

Engram-style models: Tencent's Hy4 flash (224B, 64B of it lookup tables, 12B active) has the same shape. GLM-5.3-Flash projects to about 14.5 tok/s here and needs 120 GB of disk.
